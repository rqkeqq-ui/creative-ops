# Использование AI и организация работы

## Кратко

Проект сделан одним AI-агентом в среде **OpenCode** на модели **DeepSeek v4.1 Flash**. Отдельного «роя» агентов в этой итерации не запускалось: работа велась последовательными фазами с разными ролями (исследователь → архитектор → автор тестов → разработчик → QA). Такая схема дала главное преимущество мультиагентности — разделение ответственности и проверяемые контракты между этапами — без накладных расходов на синхронизацию нескольких процессов.

AI использовался не как генератор «кода на глаз», а как исполнитель внутри жёсткого инженерного контура: **сначала требования и тесты, потом код, потом проверка**. Все артефакты лежат в репозитории и воспроизводимы.

---

## Какие инструменты применялись

| Инструмент | Роль в работе |
|---|---|
| **OpenCode** | агентная среда: чтение/запись файлов, запуск команд, тестов и браузера, навигация по коду |
| **DeepSeek v4.1 Flash** | основная модель для проектирования, написания кода и тестов, разбора падений |
| **Vitest** | быстрый контур unit / integration / API-тестов |
| **Playwright (Chrome)** | E2E-проверка реальных сценариев в браузере, трейсы и скриншоты |
| **TypeScript `tsc --noEmit` + `next build`** | статический и сборочный контроль перед каждым коммитом |
| **GitHub CLI** | публикация исходного кода |
| **SQLite `node:sqlite`** | БД без нативных зависимостей, чтобы демо поднималось одной командой |

Генерация изображений, внешние дизайн-сервисы и no-code конструкторы не использовались: интерфейс и все диаграммы сделаны кодом (Tailwind + собственный SVG), чтобы не тянуть лишние зависимости.

## Как работа была организована по шагам

### Шаг 1. Research → стек → архитектура → roadmap

Агенту был дан полный текст ТЗ. Дальше — декомпозиция на требования F1–F11, явное разделение «в скоупе / вне скоупа», сравнение вариантов стека и БД по критериям (один деплой, отсутствие нативных зависимостей, тестируемость ядра, типобезопасность).

Результат зафиксирован в `docs/01-RESEARCH.md`, `docs/02-ARCHITECTURE.md`, `docs/03-ROADMAP.md`. Важно: решения принимались до кода, поэтому позже не пришлось переписывать слои.

**Пример промпта (сокращённо):**
> «Разложи ТЗ на проверяемые требования. Сравни 5 fullstack-вариантов и 5 вариантов БД по критериям: один деплой, минимум нативных зависимостей, тестируемость домена. Предложи слои и модель данных. Зафиксируй риски и митигации».

### Шаг 2. Тесты раньше кода

Тесты писались по каждому требованию ТЗ и запускались до появления модулей. Красный прогон (11 файлов не компилируются, модулей нет) сохранён как доказательство TDD-подхода.

Покрытие контрактов:

| Требование | Тесты |
|---|---|
| Роли и запреты | `tests/integration/rbac.test.ts` |
| Валидация ТЗ | `tests/unit/validation.test.ts` |
| Матрица переходов | `tests/unit/workflow.test.ts` |
| Жизненный цикл | `tests/integration/lifecycle.test.ts`, `tests/e2e/lifecycle.spec.ts` |
| Время и просрочка | `tests/unit/time.test.ts` |
| AI-расходы | `tests/integration/ai-usage.test.ts` |
| Аналитика | `tests/unit/analytics.test.ts`, `tests/integration/analytics.test.ts` |
| Аудит | `tests/integration/activity.test.ts` |
| Демо-данные | `tests/integration/seed.test.ts` |
| HTTP-контракт | `tests/api/api.test.ts` |
| UI и RBAC в браузере | `tests/e2e/board.spec.ts`, `analytics.spec.ts` |

### Шаг 3. Код под тесты

Порядок реализации: схема БД → домен → сервисы → API → UI. На каждом этапе запускался соответствующий контур тестов.

Правило соблюдалось: **если тест падает — правится код, а не тест**. Единственная встречная правка за всю итерацию — UI-подписи статусов: на карточке задачи должно быть «Новая», а в заголовке колонки — «Новые». Это исправление интерфейса под уже зафиксированный контракт, а не ослабление проверки.

### Шаг 4. Демо и приёмка

- Ленивый автосев демо-данных при первом обращении к БД.
- 16 задач во всех статусах, просрочки, правки, история, AI-расходы.
- Скриншоты ключевых экранов (`docs/screenshots/`).
- Финальный прогон: `tsc --noEmit` → `vitest` (122) → `next build` → Playwright (10).

## Организация «нескольких агентов»

В этой итерации использовался **один агент с ролевым разделением этапов**. Причины:

1. **Контракт важнее параллельности.** Тесты и схема БД — общий контракт. Если несколько агентов пишут код одновременно, они начинают расходиться в типах и статусах; на прототипе за 24 часа это дороже, чем последовательная работа.
2. **Дешёвая проверка.** Каждая фаза заканчивалась исполняемым гейтом (тесты, typecheck, build), поэтому ошибка ловилась сразу, а не на интеграции.
3. **Прозрачность.** Один агент удерживает целостную картину домена: правила переходов, RBAC и аналитику проще согласовать в одной голове.

При этом схема легко масштабируется в мультиагентную:

```
Оркестратор (декомпозиция, приёмка)
   ├── Research/Architect  → docs/01–03, схема БД, API-контракт
   ├── Test Author         → tests/**, красный прогон
   ├── Implementer         → domain/services/api/ui под зелёный контур
   └── QA                  → typecheck, build, E2E, скриншоты
```

Ключевое условие — передача между агентами только через артефакты репозитория (документы, тесты, типы), а не через «устные» договорённости в контексте. Именно так устроена эта работа.

## Что AI сделал хорошо, а где потребовался контроль

**Хорошо:**
- декомпозиция ТЗ и проектирование state machine;
- генерация большого объёма однотипных тестов и репозиториев;
- быстрый разбор падений Playwright по трейсам и скриншотам;
- поддержание единого стиля UI без дизайн-системы.

**Потребовало ручного контроля:**
- точные подписи и тексты, которые проверяют E2E (род/число, формулировки);
- порядок таймстемпов и граничные случаи просрочки;
- типизация Route Handlers и моков в API-тестах;
- проверка, что тесты действительно падают без кода, а не «зеленеют» случайно.

## Воспроизводимость

```bash
npm ci
npm test          # 122 теста
npm run build
npm run test:e2e  # 10 сценариев
```

Все проверки проходят на чистой БД: тесты создают временные файлы SQLite, E2E — отдельную `data/e2e.db`.

---

## Итог

AI сократил время на рутину (CRUD, тесты, вёрстка, разбор ошибок), но качество обеспечил инженерный контур: требования → тесты → код → автоматические гейты. Прототип работает, покрыт тестами и готов к следующему этапу — доработке до продуктового состояния.
