# Шаг 1. Research: стек, архитектура, roadmap

> Проект: **CreativeOps** — мини-сервис управления креативным отделом (медиабайеры ↔ креативщики ↔ руководитель).

## 1. Что именно нужно (декомпозиция ТЗ)

| # | Требование ТЗ | Как трактуем в прототипе | Приоритет |
|---|---|---|---|
| F1 | Роли: байер, креативщик, руководитель | Роли в БД + RBAC-проверки в сервисном слое (не только в UI) | P0 |

## 2. Критерии выбора стека

1. Один деплой (frontend+backend+БД) — меньше времени на инфраструктуру в 24-часовом окне.
2. Минимум нативных зависимостей — окружение проверяющего может быть любым (Windows/macOS/Linux, разные Node).
3. Тестируемость ядра: бизнес-правила должны тестироваться без браузера.
4. Типобезопасность от БД до UI.
5. Возможность быстро показать «современный интерфейс» без сборки дизайн-системы с нуля.

## 3. Сравнение вариантов

### 3.1 Fullstack-фреймворк

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| **Next.js 15 (App Router) + Route Handlers** | один процесс и один деплой; серверные компоненты → быстрый первый рендер Kanban/аналитики; встроенный роутинг, кэш, `next build` как проверка типов; стандарт индустрии, легко нанимать | «магия» фреймворка, нужно знать про server/client boundary | **Выбран** |
| Vite + React SPA + Fastify/Express | прозрачность, полный контроль, лёгкий backend | два процесса, CORS, отдельная сборка/хостинг статики, больше кода на инфраструктуру, нет SSR | отклонён (время) |
| Remix / React Router 7 | хорошие data-loaders | экосистема меньше, чем у Next, ради прототипа выгоды нет | отклонён |
| Django/Rails + шаблоны | быстрый CRUD, админка «из коробки» | Kanban/аналитика на серверных шаблонах = много JS руками; найм и демонстрация хуже для этой вакансии | отклонён |
| NestJS + React | строгая слоистость, DI | заметно больше бойлерплейта под 24 часа | отклонён |

### 3.2 База данных

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| **SQLite через штатный `node:sqlite` (Node 22.5+/24)** | нулевые зависимости, нет нативных сборок и prebuild-проблем на Windows; файл БД = весь стейт демо; SQL и транзакции; один процесс | не для горизонтального масштабирования; в serverless (Vercel) файловая система эфемерна | **Выбран для демо** |
| `better-sqlite3` | зрелый, быстрый | нативная сборка под конкретный Node ABI — риск «не запустится у проверяющего» | отклонён как основной |
| Prisma + SQLite | типизация, миграции «из коробки» | тянет движок (download binary) на postinstall; для прототипа тяжёл | отклонён |
| Drizzle + better-sqlite3 | хорошая типизация, легче Prisma | опять нативная зависимость; выгода ORM не оправдана для ~6 таблиц | отклонён |
| PostgreSQL (Neon/Supabase) | продакшн-путь | требует внешних кредов → демо не поднимется «одной командой» | отложен: `Database` интерфейс абстрагирован, замена на PG — точечная задача (см. roadmap) |

Вывод: **слой доступа к данным изолирован** (`src/lib/db`), сервисы не знают про драйвер → миграция на Postgres не переписывает бизнес-логику.

### 3.3 UI

| Вариант | Комментарий | Итог |
|---|---|---|
| **Tailwind CSS v4 + собственные компоненты** | v4 без `tailwind.config.js`, быстрый старт; полный контроль над внешним видом; нет лишних 40 файлов дизайн-системы | **Выбран** |
| shadcn/ui | красиво и знакомо, но это CLI + копипаста зависимостей (Radix) — дольше и тяжелее для прототипа | отклонён |
| MUI/AntD | много готового, но «корпоративный» вид и тяжёлый JS | отклонён |
| Графики: Chart.js/Recharts vs **собственный SVG** | для 4 видов диаграмм внешняя библиотека не нужна, SSR без гидратации | собственный SVG |

### 3.4 Тесты

| Уровень | Инструмент | Что проверяем |
|---|---|---|
| Unit (ядро) | **Vitest** | матрица переходов статусов, права ролей, вычисление длительностей/просрочки, агрегации аналитики |
| Интеграционные (сервисы + реальная БД) | **Vitest** + временный файл SQLite | полный жизненный цикл задачи, RBAC-отказы, транзакции, аудит-лог, цифры аналитики |
| HTTP/API | **Vitest** против запущенного сервера | коды ответов, схема ошибок, cookie-сессия, защита от мутаций без авторизации |
| E2E (браузер) | **Playwright** (системный Chrome) | реальные сценарии: вход, создание ТЗ, взятие, сдача, правки, приёмка, аналитика |

Vitest выбран из-за скорости, нативных TS/ESM и единого раннера для unit+integration. Playwright — из-за трейсов/скриншотов как доказательства «рабочей демоверсии».

### 3.5 Аутентификация

Cookie-сессия (httpOnly, `SameSite=Lax`) + `scrypt`-хеш пароля из `node:crypto`. Альтернативы (NextAuth/Clerk) — лишняя внешняя зависимость и настройка OAuth за 24 часа. Демо-аккаунты показаны прямо на странице входа, для ручного теста достаточно одного клика.

## 4. Архитектура

```
Браузер (React 19 / server components + client islands)
        │  fetch / навигация
        ▼
Next.js Route Handlers  ──►  Services (use-cases, RBAC, транзакции)  ──►  Repository (SQL, node:sqlite)
   (тонкие: auth-guard,                                 ▲                        │
    zod-валидация, JSON)                        Domain (чистые правила)            ▼
                                          переходы статусов, время, агрегаты   SQLite (data/app.db)
```

Слои и правило зависимостей: `app → services → {domain, db}`; `domain` не знает ни про БД, ни про HTTP (поэтому тестируется мгновенно). RBAC проверяется в сервисах — UI лишь скрывает недоступные кнопки, но обойти его нельзя.

Ключевое решение по F5/F8: таймстемпы и история **append-only**, статус меняется только через action с проверкой перехода, поэтому аудит не «дорисовывается», а является побочным эффектом единственно возможного пути.

## 5. Риски и как закрываем

| Риск | Митигация |
|---|---|
| «Прототип, но не работает» | E2E Playwright на сквозные сценарии + seed с данными во всех статусах |
| Фиктивная проверка прав (только UI) | Тесты на 403 для каждой запрещённой операции |
| Расхождение «Kanban» и «истории» | Единая точка изменения статуса (`services/tasks.ts: applyAction`) |
| Демо не поднимется у проверяющего | Нет нативных зависимостей, `npm ci && npm run dev`, плюс Dockerfile |
| Публичная ссылка требует кредов | Подготовлены Dockerfile, `render.yaml`, инструкция; публичный URL выдаётся через один шаг владельца или туннель |
